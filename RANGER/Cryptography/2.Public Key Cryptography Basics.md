**Authentication**: You want to be sure you communicate with the right person, not someone else pretending.

**Authenticity**: You can verify that the information comes from the claimed source.

**Integrity**: You must ensure that no one changes the data you exchange.

**Confidentiality**: You want to prevent an unauthorised party from eavesdropping on your conversations.


Private key cryptography, i.e., symmetric encryption, mainly protects confidentiality.

public key cryptography, i.e., asymmetric cryptography, plays a significant role in authentication, authenticity, and integrity.


In reality, you need more cryptography to verify that the person you’re talking to is who they say they are. This is achieved using digital signatures and certificates.

### **==`RSA :`==**

RSA is a method for encrypting data using two keys: one to lock (encrypt) and another to unlock (decrypt) it, relying on the difficulty of factoring large number. It is a public-key encryption algorithm that enables secure data transmission over insecure channels.

The public key is known to all correspondents and is used for encryption, while the private key is protected and used for decryption, as shown in the figure below.

![Alice encrypts the message with Bob's public key and Bob decrypts it with his private key.](https://tryhackme-images.s3.amazonaws.com/user-uploads/5f04259cf9bf5b57aed2c476/room-content/5f04259cf9bf5b57aed2c476-1725294065881.svg)

|Symbol|Meaning|
|---|---|
|**p, q**|Large prime numbers|
|**n**|p × q|
|**ϕ(n)**|Euler’s Totient = (p−1)(q−1)|
|**e**|Public exponent|
|**d**|Private exponent|
|**m**|Plaintext (message)|
|**c**|Ciphertext|
#### **Key Generation Steps :**

## 1. Choose Two Prime Numbers

Select two prime numbers:

```
p = 157 q = 199
```
## 2. Compute n

Multiply the primes:

```
n = p × q n = 157 × 199 n = 31243
```

`n` is part of both the public and private keys.
## 3. Compute Euler’s Totient ϕ(n)

Using the formula:

```
ϕ(n) = n − p − q + 1
```

Substitute values:  `ϕ(n) = 31243 − 157 − 199 + 1     ANS : ϕ(n) = 30888`
## 4. Choose Public Exponent e

Choose `e` such that:

- `1 < e < ϕ(n)`
- `gcd(e, ϕ(n)) = 1`

Chosen value: `e = 163`
## 5. Compute Private Exponent d

Find `d` such that:  `e × d ≡ 1 (mod ϕ(n))`

Calculation:  `163 × 379 = 61777 61777 mod 30888 = 1`

Therefore:  `d = 379`
## 6. Keys :

Public Key : `(n, e) = (31243, 163)`

Private Key : `(n, d) = (31243, 379)`
## 7. Encrypt the Message

Plaintext: `m = 13`

Encryption formula:  `c = m^e mod n`

Substitute:  `c = 13^163 mod 31243 c = 16341`

Ciphertext sent: `c = 16341`
## 8. Decrypt the Message

Decryption formula: `m = c^d mod n`

Substitute:  `m = 16341^379 mod 31243 m = 13`

Original message recovered.
## Core Formula Summary

```
n = p × q 
ϕ(n) = n − p − q + 1 
c = m^e mod n
m = c^d mod n
```

# ==`Diffie-Hellman Key Exchange :`==


## Purpose 

```
1-> Solves the key-sharing problem in symmetric encryption
2-> Allows two parties to create a shared secret over an insecure channel
3-> No pre-shared secret required
4-> Eavesdroppers can see all exchanged values but cannot compute the secret
```

## Public and Private Values

### Public (known to everyone)

- **p**: large prime number
- **g**: generator, where 0 < g < p

### Private (never shared)

- **a**: Alice’s private key
- **b**: Bob’s private key

![[Pasted image 20260124130926.png]]
## Step-by-Step Numerical Example

### 1. Agree on Public Parameters

Chosen publicly:
```
p = 29 
g = 3
```
### 2. Choose Private Keys

Chosen secretly:
```
Alice: a = 13 
Bob: b = 15
```
### 3. Compute Public Keys

Alice computes:
```
A = g^a mod p 
A = 3^13 mod 29 
A = 19
```

Bob computes:
```
B = g^b mod p 
B = 3^15 mod 29 
B = 26
```
### 4. Exchange Public Keys

- Alice sends **A = 19** to Bob
- Bob sends **B = 26** to Alice

⚠️ This happens over an **insecure channel**
### 5. Compute Shared Secret

Alice computes:
```
s = B^a mod p 
s = 26^13 mod 29 
s = 10
```

Bob computes:
```
s = A^b mod p 
s = 19^15 mod 29 
s = 10
```

### ==`Authenticating the Server (SSH) :`==

### Authenticating the Server

![[Pasted image 20260124202325.png]]

 When you connect to a server via SSH for the **first time**, the client does **not recognize the server’s public key**.

 SSH shows a **fingerprint** (hash) of the server’s public key and asks you to confirm it.

This warning exists because a **Man-in-the-Middle (MITM) attack** is possible if the server is fake.

By typing **`yes`**, you are **trusting and authenticating the server**.

![[Pasted image 20260124202635.png]]

==`1.`== First SSH-Server sends the fingerprints to the client.

==`2.`== Then SSH-CLIENT checks that is it already present in the known hosts file if not then ->
The server’s public key is then saved in ==`~/.ssh/known_hosts`==.

==`3.`== On future connections:
- If the key is the same → connection proceeds silently
- If the key changes → SSH warns of a possible attack

**Purpose:**  
To verify that you are connecting to the **correct and legitimate server**, not an attacker.

### Authenticating the Client

After the server is authenticated, the **client (user) must prove their identity**.SSH can authenticate users using:
==`A.`== **Passwords** (less secure)
==`B.`== **SSH key authentication** (recommended)
#### How the client SSH Key Authentication works :
==`1.`== Uses a **public–private key pair**.
==`2.`== The **private key** stays on the client machine (secret).
==`3.`== The **public key** is copied to the server and stored in ==`~/.ssh/authorized_keys`==.
==`4.`== The server verifies the client by checking if the client can **cryptographically prove ownership of the private key**.

### Key Generation

- Keys are generated using ==`ssh-keygen`==.
- Multiple algorithms are supported (RSA, DSA, ECDSA, Ed25519).
- **Ed25519** is commonly used due to strong security and smaller key size.

### SSH Private Keys

 **Private SSH keys must be kept secret**, just like passwords. Anyone with your private key can log in to servers that trust it. A **passphrase** only encrypts the private key locally ,It does **not** authenticate you to the server and It is **never transmitted** over the network.Encrypted keys can be attacked (e.g., with **John the Ripper**), so strong passphrases matter.

#### Key Handling Best Practices

- Generate SSH keys on your **local machine**.
- Copy **only the public key** to the server (e.g., using `ssh-copy-id`).
- The private key should **never exist on the target machine**.
- Private key permissions must be **600 or stricter**, or SSH will ignore the key.
- Use `ssh -i privateKeyFile user@host` to specify a key.

#### Keys Trusted by the Remote Host

- SSH keys are stored in the ==`~/.ssh`== directory.
- ==`authorized_keys`== contains **public keys allowed to log in**.
- Key-based authentication is **more secure than passwords**.
- Root SSH access should allow **keys only**, not passwords

#### Using SSH Keys for a “Better Shell”

- SSH keys can be used to **upgrade unstable reverse shells**.
- Provides a stable shell with  :  Tab completion and Proper Ctrl-C handling.
- Common in **CTFs, pentesting, and red teaming**.
- Adding a public key to `authorized_keys` can act as a **persistent backdoor**.

# Digital Signatures and Certificates

#### Digital Signature 

A digital signature is a cryptographic technique used to verify the **authenticity**, **integrity**, and **non-repudiation** of a digital message or document.In the digital world, **digital signatures** replace handwritten signatures.Only the owner of the private key can create a valid signature.

Digital signatures use **asymmetric cryptography**:

- Signed with a **private key**
- Verified with the **public key**

![[Pasted image 20260124212740.png]]
### How Digital Signatures Work

- The sender creates a **hash** of the document.
- The hash is **encrypted with the sender’s private key**.
- The receiver:
    - Decrypts the hash using the sender’s public key
    - Hashes the received document
    - Compares both hashes
- Matching hashes prove **authenticity and integrity**.

## Certificates

A certificate is a digital document that binds a **public key** to the identity of an individual, organisation, or website. It is issued and signed by a **Certificate Authority (CA)** to prove the owner’s identity.

Certificates prove the **identity of a website or entity**.Commonly used in **HTTPS**.

Certificates rely on a **chain of trust**:
- Website certificate → signed by an organisation
- Organisation → trusted by a **Certificate Authority (CA)**
- CA → trusted by your browser/OS
- Browsers trust certificates only if the **Root CA** is trusted.

### TLS Certificates & HTTPS

- HTTPS requires a **TLS certificate**.Modern websites should always use **HTTPS** for security.

- Certificates can be:
    - Purchased from Certificate Authorities
    - Obtained **for free** using **Let’s Encrypt**

 [Let's Encrypt](https://letsencrypt.org/)  It provides free TLS certificates.

# PGP and GPG

**PGP** stands for Pretty Good Privacy. It’s software that implements encryption for encrypting files, performing digital signing, and more. [GnuPG or GPG](https://gnupg.org/) is an open-source implementation of the OpenPGP standard.

GPG is commonly used in email to protect the confidentiality of the email messages. Furthermore, it can be used to sign an email message and confirm its integrity.

**GPG Key Pair :**  A GPG key pair consists of a **public key** and a **private key** used for encryption and digital signatures.
#### Key Roles
- **Public key:** Shared with others to encrypt messages for you
- **Private key:** Kept secret; used to decrypt messages and sign data

### Practical GPG Usage

### Import a Key

Adds a GPG key to your keyring.

```
gpg --import backup.key
```

### Decrypt a File

Uses your private key to decrypt encrypted data.

```
gpg --decrypt confidential_message.gpg
```
