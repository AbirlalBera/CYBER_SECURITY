
#### **What is File inclusion?**

**File inclusion** is a web application vulnerability where an attacker can make a server **load or execute unintended files**.

![[Pasted image 20260109011919.png]]

![[Pasted image 20260109011926.png]]

#### **Why do File inclusion vulnerabilities happen?**

File inclusion vulnerabilities happen due to **poor input validation** in web applications.When user-controlled input is **not properly sanitized or validated**, attackers can manipulate it to load unintended files. This is common in poorly implemented applications (e.g., PHP), where developers allow user input to directly control file-handling functions, leading to the vulnerability.

#### **What is the risk of File inclusion?**

The risk of **File Inclusion** is that attackers can **read sensitive files** on the server, such as source code, credentials, configuration files, or system files.  
If the attacker is also able to **upload or write files** to the server, the vulnerability can be escalated to **remote command execution (RCE)**, allowing full compromise of the system.

#### **Path Traversal**

Also known as Directory traversal, a web security vulnerability allows an attacker to read operating system resources, such as local files on the server running an application. The attacker exploits this vulnerability by manipulating and abusing the web application's URL to locate and access files or directories stored outside the application's root directory.>

Path traversal vulnerabilities occur when the user's input is passed to a function such as file_get_contents in PHP. It's important to note that the function is not the main contributor to the vulnerability. Often poor input validation or filtering is the cause of the vulnerability. In PHP, you can use the file_get_contents to read the content of a file.

### **LFI Local File Inclusion** 

LFI attacks against web applications are often due to a developers' lack of security awareness. With PHP, using functions such as **include, require, include_once, and require_once** often contribute to vulnerable web applications.

# LFI scenarios


###### **Source Code**

**1. Suppose the web application provides two languages, and the user can select between the EN and AR**

```php
<?PHP 
include($_GET["lang"]);
?>
```

The PHP code above uses a GET request via the URL parameter lang to include the file of the page. The call can be done by sending the following HTTP request as follows: `http://webapp.thm/index.php?lang=EN.php` to load the English page or `http://webapp.thm/index.php?lang=AR.php` to load the Arabic page, where EN.php and AR.php files exist in the same directory.

Theoretically, we can access and display any readable file on the server from the code above if there isn't any input validation. Let's say we want to read the `/etc/passwd` file, which contains sensitive information about the users of the Linux operating system, we can try the following: `http://webapp.thm/get.php?file=/etc/passwd`

In this case, it works because there isn't a directory specified in the include function and no input validation.


**2.** Next, In the following code, the developer decided to specify the directory inside the function.

```php
<?PHP 
include("languages/". $_GET['lang']); 
?>
```

In the above code, the developer decided to use the include function to call PHP pages in the languages directory only via lang parameters.

If there is no input validation, the attacker can manipulate the URL by replacing the lang input with other OS-sensitive files such as /etc/passwd.

Again the payload looks similar to the path traversal, but the include function allows us to include any called files into the current page. The following will be the exploit:

```
http://webapp.thm/index.php?lang=../../../../etc/passwd
```


###### **Error Based**


3.**Vulnerable Entry Point:** http://webapp.thm/index.php?lang=EN

 Full error: 
```
 Warning: include(languages/THM.php): failed to open stream... in /var/www/html/THM-4/index.php on line 12
```
 Reveals:
- Include pattern: include("languages/" . $lang . ".php");
- Appends .php automatically to user input.
- Full server path: /var/www/html/THM-4/

**Goal:** Read arbitrary files (e.g., /etc/passwd) via directory traversal.

**Initial Attempt (Traversal):** 
```
?lang=../../../../etc/passwd 

Becomes: 

include("languages/../../../../etc/passwd.php") → Still appends .php → fails (tries to open passwd.php).
```

**Bypass Technique: Null Byte (%00)**

 Null byte (\0 or %00 URL-encoded) terminates string processing in older PHP versions (< 5.3.4).
 
 Anything after %00 is ignored by certain PHP functions (like include when handling strings).
 
 Payload tricks the code into: include("languages/../../../../etc/passwd%00" . ".php"); → Effectively becomes: include("languages/../../../../etc/passwd");

**Exploitation Payload:** http://webapp.thm/index.php?lang=../../../../etc/passwd%00

**Why it works:**

- Traversal (../../../../) escapes /var/www/html/THM-4/languages/ to root.
- %00 cuts off the forced .php extension.

**Note:**

- Null byte bypass was patched in PHP 5.3.4+. Works only on older/unpatched systems.
- Common LFI target: /etc/passwd to list users

## 4 – Bypassing Keyword Filters (`/etc/passwd`)

 **Some apps block sensitive keywords like `/etc/passwd`**

```

Bypass techniques:

Null byte injection:

/etc/passwd%00

 Current directory trick (`/.`):

/etc/passwd/.

```

**Reason:**

. refers to the current directory, so /etc/passwd/. still resolves to /etc/passwd . Filters often fail to normalize paths properly

## 5 – Bypassing `../` Input Validation

 App removes `../` from user input
 
- Example error shows:

```include(languages/etc/passwd)```

- **Bypass payload**:

`....//....//....//....//etc/passwd`

- Why it works:

- Filter replaces only the **first occurrence** of `../`

- Remaining traversal sequences still resolve to valid paths
